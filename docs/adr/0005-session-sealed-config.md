# ADR-0005: コンフィグはセッション内で不変とし、更新は次回起動から適用する

- **状態**: 承認
- **決定日**: 2026-07-30

## 背景

SDK はバックグラウンドでコンフィグを取得する。取得した新しいコンフィグを**いつから使うか**。

## 選択肢

### A. 即時反映
取得した瞬間から新しいコンフィグで評価する。

- ✅ 実験の変更が最速で反映される
- ❌ **同一セッション中に UI が変わる**。ホーム画面では旧バリアント、次の画面では新バリアント、という状態が起きる
- ❌ **曝露の意味が壊れる**。1 ユーザが同一実験で複数バリアントに曝露され、解析上どちらに属するか決まらない
- ❌ 評価が純関数でなくなり、呼ぶタイミングで結果が変わる。デバッグが著しく困難になる

### B. セッション内シール（起動時に確定し、セッション中は不変）
起動時にロードしたコンフィグをセッション終了まで使う。取得した新しいコンフィグはディスクに保存し、**次回起動から**有効にする。

- ✅ セッション中の UI が一貫する
- ✅ **曝露が 1 ユーザ 1 バリアントに保たれる**
- ✅ 評価が純関数になり、ロックなしで any スレッドから呼べる
- ❌ 変更の反映が「次回起動」まで遅れる

### C. 画面遷移などのセーフポイントで反映
アプリが定義した「安全な境界」で切り替える。

- △ A と B の中間だが、**どこが安全かをアプリ開発者が判断する必要がある**。判断ミスが A と同じ事故を招く
- ❌ SDK の API が複雑化し、正しく使うのが難しくなる

## 決定

**B（セッション内シール）** を採用する。フォアグラウンド復帰時にセッションが更新された場合（前回のバックグラウンド遷移から 30 分以上経過）は、そのタイミングで再シールする。

### 決め手

**曝露の一意性は統計の前提条件**であり、破ると実験結果そのものが無意味になる。1 人のユーザが control と treatment の両方に曝露された場合、そのユーザをどちらの群として数えても効果推定にバイアスが入る（除外してもセレクションバイアスが入る）。

一方、「反映が次回起動まで遅れる」ことの実害は小さい:

- モバイルアプリのセッションは通常数分。次回起動は多くの場合その日のうちに来る。
- 緊急停止（キルスイッチ）も次回起動で効く。**アプリが起動していないユーザには、そもそも何の影響も及んでいない**ので、これで十分。
- 実験の開始・停止は数時間〜数日の単位の操作であり、分単位の即時性は要求されない。

## 帰結

### 実装への影響

- `SealedConfig` を**不変オブジェクトの原子的差し替え**として実装する。これにより評価パスからロックを完全に排除でき、`variant()` を任意のスレッドから 10ms 予算内で呼べる（[docs/04-client-sdk.md](../04-client-sdk.md)）。この性能特性はこの ADR の副次的な利得。
- WebSocket / SSE によるコンフィグ push が不要になる。モバイルで常時接続を維持するバッテリー・接続管理コストを丸ごと回避できる（[docs/03-tech-selection.md](../03-tech-selection.md) の不採用リスト）。

### 受け入れるコスト

- **初回起動時にコンフィグがない問題（C6）が顕在化する。** 即時反映なら「起動直後に取得して即反映」で誤魔化せるが、この決定ではそれができない。対応としてバイナリ同梱デフォルトを必須にし、「初回セッションから効かせたい実験はリリースビルド時点でコンフィグに含まれている必要がある」という運用制約を受け入れる。
- **QA 時は不便。** コンフィグを変えても再起動しないと反映されない。デバッグメニューに「強制リロード + 即時再シール」を用意し、QA 時のみこの規則を破れるようにする。

### 例外

| ケース | 扱い |
|---|---|
| `sdk_kill` によるSDK 自体の無効化 | **即時適用**。SDK に重大なバグがある場合の最終手段なので、一貫性より停止を優先する |
| デバッグメニューからの強制リロード | 即時適用（QA 用途、リリースビルドでは社内 ID 検証の背後） |
| 30 分以上のバックグラウンド後の復帰 | 新セッションとみなして再シール。曝露も新セッションとして記録するため一意性は保たれる |
