# ADR-0004: バケッティングに SHA-256 を用いる（MurmurHash3 を採らない）

- **状態**: 承認
- **決定日**: 2026-07-30

## 背景

決定的割当のハッシュ関数を選ぶ。この選択は**一度決めたら実質変更できない** — 変更すれば全ユーザの割当がシャッフルされ、稼働中の全実験が壊れる。

## 選択肢

| 関数 | 速度 | 実装の一意性 | 標準ライブラリ |
|---|---|---|---|
| MurmurHash3 | 非常に速い（〜10ns） | ❌ **亜種が多い** | ❌ 外部依存が必要 |
| xxHash / FNV-1a | 速い | △ | ❌ |
| **SHA-256** | 遅い（〜500ns） | ✅ **完全に一意** | ✅ 全言語にある |
| MD5 | 中 | ✅ | ✅（ただし FIPS 環境で禁止されることがある） |

## 決定

**SHA-256** を採用する。

### 根拠

**1. MurmurHash3 には実装のバリエーションが多すぎる。**

- `x86_32` / `x86_128` / `x64_128` の 3 系統があり、同じ入力でも結果が違う。
- シードの解釈、末尾バイトの処理、符号の扱いが実装ごとに揺れる。
- 主要な A/B テスト基盤（Optimizely、GrowthBook）が MurmurHash3 x86_32 を使っているため「業界標準」に見えるが、**その選択はブラウザでの実行速度が動機**であり、モバイルアプリには当てはまらない。

Swift / Kotlin / Go / Python / TypeScript の 5 言語で MurmurHash3 の実装を揃え、それが未来にわたって一致し続けることを保証するのは、得られる速度に対して割に合わないリスク。

**2. 速度差が問題にならない。**

SHA-256 は MurmurHash3 の 50 倍遅いが、絶対値は 1 回あたり約 500ns。アプリ起動時に評価するフラグを 50 個としても合計 25μs で、`start()` の予算 10ms の 0.25% にすぎない。**測定できないほど小さい差のために、決定性のリスクを取る理由がない。**

**3. 標準ライブラリだけで完結する。**

[ADR-0003](0003-native-sdks.md) で「SDK は依存ライブラリを持たない」を制約にしている。MurmurHash3 は自前実装するか外部依存を持つことになり、前者は §1 のリスクを、後者はホストアプリとの衝突リスクを生む。

`CryptoKit`（iOS）と `MessageDigest`（Android）は OS 標準で、追加コストがゼロ。

**4. 暗号学的強度は必要ないが、害もない。**

割当予測の防止は目的ではない（コンフィグ自体が公開情報なので、そもそも誰でも自分の割当を計算できる）。SHA-256 を選ぶ理由は強度ではなく**実装の一意性**である。この点を誤解しないよう明記しておく。

## 帰結

- 剰余バイアス（`2^32 mod 10000 = 7296`、相対 1.7×10⁻⁶）は許容する。棄却サンプリングによる補正は実装を複雑にし、言語間の不一致リスクを上げるだけ。詳細は [spec/bucketing.md §4](../../spec/bucketing.md#4-剰余バイアスについて)。
- **符号なし 32 ビットとして読むこと**を規範仕様で強制する。Java / Kotlin には `uint32` がないため、`ByteBuffer.getInt()` の結果をそのまま使うと負値になり、`%` の結果が言語ごとに変わる（C 系は負、Python は正）。これが最も起きやすい実装事故であり、ゴールデンベクタに `uint32_be` を含めているのはこの段階での不一致を検出するため。
- 将来ハッシュ関数を変更する場合、既存の全実験を終了させてからでないと実施できない。実質的に不可逆な決定として扱う。
