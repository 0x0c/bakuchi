# ADR-0001: 自前構築か既製品か

- **状態**: 承認
- **決定日**: 2026-07-30

## 背景

A/B テスト基盤には成熟した選択肢が複数ある。自前構築の前に、買う／借りる選択肢を潰しておく必要がある。

## 選択肢

| 選択肢 | 費用感 | 長所 | 短所 |
|---|---|---|---|
| **Firebase A/B Testing / Remote Config** | 無料〜低額 | 導入が数日。モバイル SDK が枯れている | 統計機能が貧弱（ベイズのみ、CUPED なし、SRM 診断なし）。レイヤー排他なし。自社 DWH のメトリクスを使えない |
| **GrowthBook（OSS・自己ホスト）** | インフラ費のみ | 自社 DWH のデータをそのまま使える。統計手法が正当（ベイズ／頻度論、CUPED、逐次検定）。SDK が多言語 | モバイル SDK の作り込みは自社製より浅い。運用は自前 |
| **LaunchDarkly / Optimizely / Statsig** | 数百万〜数千万円/年（MAU 従量） | 全部入り。サポートあり | MAU 課金がスケールに対して線形に効く。データが外部に出る。モバイル固有の要件（バンドルデフォルト等）に手が届かない |
| **自前構築** | 人件費（初期 4〜6 人月 + 運用） | 完全な制御。既存基盤との統合。モバイル固有の課題に最適化 | 構築・運用コスト。統計を誤ると害のほうが大きい |

## 決定

**以下の条件をすべて満たす場合にのみ自前構築する。満たさない場合は GrowthBook を自己ホストする。**

1. MAU 100 万以上（SaaS の MAU 課金が自前構築の人件費を上回る規模）
2. 年間実験数 50 本以上（基盤への投資が回収できる利用頻度）
3. 実験基盤に責任を持つ専任が 2 名以上いる（構築後の運用が最大のコスト）
4. 自社 DWH の複雑なメトリクス定義を実験に使う必要がある
5. モバイル固有の要件（バイナリ同梱デフォルト、レイヤー排他、オフライン耐性）が既製品で満たせないことを PoC で確認済み

条件 3 が最も見落とされる。**基盤は作った後のほうが長い。** 統計手法の検証、データ品質の監視、実験設計の相談対応は継続的な仕事であり、これを担う人がいない基盤は「動いているが誰も結果を信じない」状態に落ちる。

## ハイブリッドという選択肢

見落とされがちだが有力な中間解:

- **配信は GrowthBook / Firebase、解析は自社 DWH** — 曝露イベントだけ自社の基盤に流し、統計判定は自前で作る。最も重い「モバイル SDK」を作らずに済み、最も価値の高い「自社メトリクスでの正しい統計」を得られる。
- Phase 1 をこの形で始め、SDK の作り込みが本当に必要になってから自前化する経路は合理的。
