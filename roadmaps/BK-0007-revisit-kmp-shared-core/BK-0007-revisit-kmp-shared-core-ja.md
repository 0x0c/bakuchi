## はじめに

[BK-0003](../BK-0003-native-sdks/BK-0003-native-sdks-ja.md) は Swift と Kotlin のネイティブ 2 実装
を出荷し、共有 Kotlin Multiplatform コアを却下しました。この却下は技術そのものの評価ではなく、
現時点の SDK の規模に依拠しています。つまり、誰も気づかないうちに正しくなくなりうる判断です。

本項目は、その逆転を観測可能にします。判断を再開する条件をあらかじめ記録し、二重に書く作業へ最も
疲れた人の裁量ではなく、証拠によって再開が決まる状態を作ります。

## 動機

規模を根拠とする判断には、明示された引き金が必要です。規模は静かに変わるためです。引き金がないと、
起こりやすく、どちらも望ましくない結末が 2 つあります。1 つは、共有したほうが安くなる地点をとうに
過ぎても 2 実装を保守し続ける結末です。文書化された判断を覆すことが、蒸し返しのように感じられる
ためです。もう 1 つは、無関係な作業の途中で、ある日の苛立ちを根拠に、移行費用を正当化する証拠が
ないまま覆してしまう結末です。

引き金を書き出しておくことで、この問いを好みの問題から事実の問題に変えられます。

## 詳細設計

### 引き金となる条件

以下の**いずれか 1 つ**が成立したとき、判断を再開します。どれも裁量ではなく観測で決まるように
選んであります。

1. **SDK のコアがどちらかのプラットフォームで 5,000 行を超えた**とき（テストとプラットフォーム固有の
   入出力を除く）。BK-0003 の却下は、共有できる範囲が小さいことに依拠しています。この規模を超えると
   その前提が成り立ちません。
2. **両実装の挙動差に起因する不具合が 2 件以上発生した**とき。1 件は誤りですが、2 件は傾向です。
   規範仕様とゴールデンベクタが、覆っていると想定していた範囲を実際には覆えていないことの直接的な
   証拠になります。
3. **ターゲティングオペレータの追加が四半期に 2 回以上発生し**、二重作業が開発速度を目に見えて
   落としているとき。2 実装の費用は変更の頻度に比例するため、頻度が継続的に上がれば計算が変わります。

### 再開時に評価すること

引き金に達しても、問いが開くだけで結論は出ません。評価では次を秤にかけます。

| 要因 | 測るもの |
|---|---|
| バイナリサイズ | 公称値ではなく、共有コアを載せたリリースビルドの実測増分 |
| 起動時間 | Kotlin/Native ランタイムを載せても `start()` が 10ms の予算に収まるか |
| Swift 側の使い勝手 | 生成された API が呼び出し側でどう読めるか。suspend 関数の橋渡しを含みます |
| 移行費用 | 既存の呼び出し箇所を移す作業量と、それを出荷するリリースリスク |
| チームの同意 | iOS チームがバイナリ増分を受け入れるか |

最後の行は要因ではなく関門です。iOS チームが採用しない SDK には価値がありません。もとの判断を生んだ
のと同じ論拠です。

### どちらに転んでも変わらないこと

本項目がどう結論しても、言語をまたいだ一致を保証するのはゴールデンベクタです。共有コアの採用は乖離の
**発生源**を 1 つ減らしますが、一致を検証する必要そのものはなくなりません。
[BK-0002](../BK-0002-local-evaluation/BK-0002-local-evaluation-ja.md) により、サーバ側の Go と
Python の実装は別のまま残るためです。モバイルのコアを共有することは、問題の解決ではなく縮小です。

## 検討した代替案

- **引き金を記録せず、将来の裁量に委ねる。** 却下します。動機の節で挙げた 2 つの失敗、すなわち文書化
  された判断への遠慮による手遅れの逆転と、ある日の苛立ちを根拠とした早すぎる逆転を招くためです。
- **期日を決めて移行を確約する。** 却下します。2 実装の費用は変更の頻度に比例し、頻度を期日は予測
  しません。日程で移行すると、もとの前提がまだ成り立っているうちに移行費用を払う恐れがあります。
- **引き金が引かれたとき、Kotlin Multiplatform ではなく Rust コアを採用する。** 却下せず、開いた
  ままにします。本項目を再開する場合、Rust の選択肢も Kotlin Multiplatform と並べて評価します。
  どちらにも味方しなかったバイナリ費用の比較が、その時点では違って見える可能性があるためです。

## 進捗

- [ ] 保留。3 つの引き金を監視し、いずれかが引かれるまで作業しません。
- [ ] SDK コアの行数を CI で追跡し、引き金 1 を推測ではなく観測にする。
- [ ] プラットフォーム間の挙動差に起因する不具合にラベルを付け、引き金 2 を数えられるようにする。
