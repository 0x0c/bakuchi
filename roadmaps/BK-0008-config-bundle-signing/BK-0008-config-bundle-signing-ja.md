## はじめに

コンフィグバンドルは CDN を通じて HTTPS で配信されます。
[`docs/04-client-sdk-ja.md`](../../docs/04-client-sdk-ja.md) のクライアント SDK 設計では、署名検証を
「任意だが推奨」と記しています。これは判断ではありません。本項目は、署名検証を必須にすることを
提案します。ビルドサービスが全バンドルに Ed25519 で署名し、SDK がアプリに埋め込んだ公開鍵で検証
します。

## 動機

[BK-0002](../BK-0002-local-evaluation/BK-0002-local-evaluation-ja.md) のもとでは、バンドルは実験を
記述するだけのものではありません。**アプリがどのコードを実行するかを決めるもの**です。改ざんされた
バンドルは、未発表の機能を有効化し、安全確認を無効化し、プラットフォームが一度も公開していない
バリアントへユーザを流し込めます。偽造されたバンドルの影響範囲は、不良リリースの影響範囲と同じで
ありながら、リリースを経ずに広がります。

通信路の保護だけでは、この隙間は実務上ふさがりません。企業のモバイルデバイス管理はルート証明書を
配布して TLS 通信を検査することがよくあり、応答を書き換えられる中間装置が、正当な理由で実ユーザの
端末に置かれています。バイナリ内の鍵で検証する署名は、結果を信頼しなければならない当事者自身が
端から端まで確認するものです。通信路の保護が及ばない場所で成立するのは、そのためです。

費用は小さく、しかも一方的です。Ed25519 の検証は 1 ミリ秒を大きく下回り、署名は 64 バイトを足すだけ
で、両プラットフォームとも標準の暗号フレームワークで提供しています。
[BK-0003](../BK-0003-native-sdks/BK-0003-native-sdks-ja.md) の無依存制約に無理をかけません。

## 詳細設計

### 署名

`config-builder` は、バンドルをコンパイルしたあとに署名します。署名の対象は `signature`
フィールドを除いたバンドルの正規化表現とします。キーの順序や空白に左右されず、検証を一意に定義
するためです。署名は base64 でエンコードし、
[`spec/config-bundle.schema.json`](../../spec/config-bundle.schema.json) が既に予約している
`signature` フィールドで運びます。

秘密鍵は Secrets Manager に置き、`config-builder` だけが到達できるようにします。人が鍵を保持する
ことはなく、ほかのサービスは署名できません。

### 検証

SDK はバンドルを採用する前に検証します。この確認は既存の検証手順、すなわちスキーマ適合と
`config_version` が保持中のものより新しいことの確認と並びます。検証に失敗したバンドルは破棄し、
以前のコンフィグを保持します。破損したバンドルや途中で切れたバンドルに対して既に取っている経路と
同じです。したがって検証失敗は新しい失敗経路ではなく、
[BK-0005](../BK-0005-session-sealed-config/BK-0005-session-sealed-config-ja.md) が SDK に既に要求
している経路の再利用です。

SDK は検証失敗をヘルスメトリクスとして報告します。多数の端末で同時にこのメトリクスが上がることは、
署名側の不具合か、実際の改ざんの試みかを意味するため、呼び出しに値するシグナルです。

### 鍵のローテーション

**アプリには公開鍵を 2 つ埋め込み**、どちらかに一致すれば検証成功とします。これにより、古いアプリ
バージョンを取り残さずに鍵を交換できます。現行鍵と次期鍵の両方を持つアプリバージョンを配信し、
普及を待ってから、署名を次期鍵に切り替えます。

ローテーションの設計が、この仕組みを生存可能にします。鍵の枠が 1 つしかないと、鍵が漏れた場合に、
新しいコンフィグを配る前にアプリのリリースが必要になります。その間、プラットフォーム唯一の緊急停止
手段であるキルスイッチが使えません。ローテーション経路をいま設計しておくことが、この事態を回復不能
にしないための備えです。

## 検討した代替案

- **HTTPS だけに頼る。** 現状であり、却下します。デバイス管理による TLS 検査は実端末上の実在する
  設定であり、応答を書き換えられる中間装置は仮定ではなく現実的な位置にあるためです。
- **署名ではなく証明書ピンニングを使う。** 却下します。ピンニングが守るのは成果物ではなく通信路
  です。CDN へ届く前に改変されたバンドルを検出できず、証明書の更新時には正当な理由で壊れます。
- **共有鍵によるメッセージ認証コードを使う。** 却下します。共有鍵はアプリ内に同梱され、誰でも
  取り出してバンドルを偽造できるためです。クライアント側の検証に意味を持たせるのは非対称署名です。
- **リリースビルドでだけ署名する。** 却下します。開発時に走らない確認は、必要な場面でテストされて
  いない確認です。ステージング環境には専用の鍵で署名します。

## 進捗

- [ ] `config-builder` での Ed25519 署名。鍵は Secrets Manager に保持します。
- [ ] 両 SDK での検証。公開鍵の枠を 2 つ埋め込みます。
- [ ] 検証失敗のヘルスメトリクスと、端末横断での上昇に対するアラート。
- [ ] ローテーション手順書の整備と、運用に依存する前の 1 回の実地演習。
