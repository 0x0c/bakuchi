## はじめに

SDK はバックグラウンドでコンフィグを取得します。本項目が決めるのは、**取得した新しいコンフィグを
いつから使うか**です。

セッション内シールを採用します。起動時に読み込んだコンフィグをセッション終了まで使い、セッション中
に取得したコンフィグはディスクに保存して、次回起動から適用します。

## 動機

届いた瞬間に新しいコンフィグを適用する方式は、無害に見えて無害ではありません。1 つのセッションの
なかで、ホーム画面では control、2 画面先では treatment という割当が起こりえます。ユーザの目の前で
画面が変わるうえ、より深刻な帰結として、**そのユーザは同一実験の両方のバリアントへ曝露した扱いに
なります**。

曝露の一意性は、あれば望ましい性質ではなく、統計の前提条件です。両方に曝露したユーザを control と
して数えれば推定に偏りが入り、treatment として数えれば逆向きの偏りが入ります。除外すればセレクション
バイアスが入ります。コンフィグ変更の瞬間にオンラインだったユーザは、無作為な標本ではないためです。
下流のどの解析でも回復できず、しかも壊れたことが見えません。数値は数値の顔をしたままです。

反対側の代価は小さく済みます。モバイルのセッションはたいてい数分で、次回起動は多くの場合その日の
うちに訪れます。キルスイッチも次回起動で効きますが、それで十分です。**アプリを起動していないユーザ
は、そもそも実験の影響を受けていない**からです。実験の開始と停止は数時間から数日の単位で行う操作
であり、分単位の即時性を必要としません。

## 詳細設計

### 採用する方式

`start()` で読み込んだコンフィグを不変の `SealedConfig` として公開し、セッション全体で使います。
バックグラウンドのフェッチは結果を検証してディスクへ書き込みますが、シール済みのスナップショットには
触れません。バックグラウンドに 30 分以上滞在してからフォアグラウンドに戻った場合は、新しいセッション
とみなして再シールします。

`SealedConfig` を不変オブジェクトの原子的差し替えとして実装すると、評価パスからロックが完全に消え
ます。`variant()` を任意のスレッドから 10ms の起動予算内で呼べるのはそのためであり、この性質は別個の
設計目標ではなく本判断の帰結です。

この判断はまた、持続的接続によるコンフィグの push を不要にします。即時配信しても受け取る相手がいない
ためです。ソケットを開き続けずに済むことで、モバイルの push 経路が伴う電池と接続管理の費用を丸ごと
回避できます。

### この判断が受け入れる代価

シールは、初回起動時にコンフィグがない問題を隠さずに表面化させます。即時適用であれば「起動直後に
取得して即反映」で初回起動を糊塗できますが、シールではできません。答えはバイナリに同梱するデフォルト
コンフィグと、そこから導かれる運用規則です。すなわち、**初回セッションから効かせたい実験は、
リリースビルドを作る時点でコンフィグに含まれている必要があります**。これを可能にするため、CI が
リリースビルド時に現行コンフィグをスナップショットして同梱します。曝露イベントには必ず
`config_source` を載せます。同梱コンフィグで評価されたユーザを、解析時に区別するためです。

QA でも不便になります。コンフィグを変えても再起動しないと反映されません。デバッグメニューの強制
リロードはそのために用意するもので、この規則を意図的に破ってよい唯一の場所です。

### 例外

| ケース | 扱い |
|---|---|
| SDK 自体を無効化する `sdk_kill` | **即時適用**します。SDK に重大な欠陥があるとき、停止することが一貫性に優先します |
| デバッグメニューからの強制リロード | 即時適用します。QA 用途であり、リリースビルドでは社内 ID 検証の背後に置きます |
| バックグラウンドに 30 分以上滞在後の復帰 | 新しいセッションとみなして再シールします。曝露も新しいセッションとして記録するため、一意性は保たれます |

## 検討した代替案

- **即時適用する。** 却下します。統計の前提条件である曝露の一意性が壊れるためです。画面のちらつきは
  目に見える症状でしかありません。実際の代価は、実験そのものが無効になる点です。
- **アプリが宣言する安全な地点で適用する**（画面遷移など）。却下します。どの地点なら安全かを、
  アプリ開発者が判断しなければなりません。判断を誤れば、即時適用と同じ失敗が起きます。SDK の API
  も複雑になり、誤用の可能性が上がります。
- **起動時にフェッチ完了までアプリをブロックし、常に最新のコンフィグを適用する。** 却下します。
  すべてのユーザで起動時間が悪化し、しかも電波の弱いユーザで最悪になります。もともと最も条件の悪い
  ユーザに、さらに不利益が集中します。
