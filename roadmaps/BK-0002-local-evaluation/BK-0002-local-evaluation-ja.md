## はじめに

どのバリアントをユーザに見せるかを決める場所には、2 つの選択肢があります。**リモート評価**では、
アプリが起動時にサーバへ問い合わせ（「私はこういうユーザです、私のフラグを教えてください」）、
サーバが解決済みの割当を返します。**端末内評価**では、サーバが全実験の定義とターゲティング条件を
含むコンフィグ全体を配信し、各端末が自分で決めます。

本項目は、モバイルの主経路として端末内評価を採用します。サーバ側評価は、バックエンドの実験と、
端末をまたいで維持するスティッキー割当のためだけに残し、モバイルアプリが起動時に依存する経路には
しません。

## 動機

この判断は、Web には対応物のないモバイルアプリの性質から導かれます。**出荷済みバイナリはデプロイ
では巻き戻せない**という性質です。不具合のあるコードを戻すには新しいビルドを提出し、ストア審査を
待ち、さらにユーザの更新を待つ必要があります。それが完了するまで、暴走した実験を止める手段は
リモートのキルスイッチだけです。

したがってコンフィグ配信は、あれば便利な機能ではありません。アプリ内の全実験にとって唯一の緊急停止
手段であり、**その可用性がアプリの可用性そのもの**になります。どちらの評価方式を採るかという議論は、
まずこの基準の上で決着させる必要があります。

リモート評価は、この最重要経路を、リクエストごとにターゲティング条件を解決する動的なアプリケーション
サーバの背後に置きます。端末内評価は、同じ経路をオブジェクトストレージ上の静的ファイルと CDN に
落とし込みます。2 つの可用性の差は、ほかのあらゆる考慮を上回るだけの大きさがあります。本項目の残り
は、選択をもう一度秤にかける話ではなく、その結果として生じる代価を支払う話です。

ここからさらに 2 つの帰結が続き、どちらも独立に端末内評価を支持します。評価が同期的になり、
ネットワーク遅延がなくなるため、`await` なしで UI スレッドからフラグを読めます。そしてアプリが
オフラインでも動作します。モバイルのセッションには、使える通信がない状態で始まるものが相当の割合で
含まれるため、この性質には意味があります。

## 詳細設計

### 2 つの選択肢

| | リモート評価 | 端末内評価 |
|---|---|---|
| 可用性の性質 | 動的サービス。リクエストごとにターゲティングを解決します | CDN 前段の静的オブジェクト |
| 評価のレイテンシ | 起動時にネットワーク往復が 1 回入ります | ありません。メモリ上の純関数です |
| オフライン時の挙動 | 利用できません | キャッシュから完全に動作します |
| サーバ側属性でのターゲティング | 利用できます | アプリが渡した属性にかぎられます |
| コンフィグの秘匿 | 割当だけが渡ります | コンフィグ全体が端末に渡ります |
| 割当ロジック | 実装は 1 つです | 言語ごとに実装が必要で、適合性テストが要ります |
| 月間アクティブユーザ 1000 万での要求数 | 1 日 3000 万の動的リクエスト | 同数ですが、キャッシュ可能で大半が `304` になります |

### 採用する構成

モバイルの全経路で端末内評価を採用します。サーバは不変のコンフィグバンドルを公開し、`config-edge`
が `ETag` 付きで配信します。SDK はバンドルをキャッシュし、同期的に評価し、フェッチでアプリを
ブロックしません。`assignment-service` は、バックエンドの実験と、端末をまたいで維持する必要のある
スティッキー割当にサーバ側評価を提供します。モバイルの起動経路が `assignment-service` に依存する
ことはありません。

この構成が生む障害時の挙動こそが設計の眼目です。CDN が落ちても SDK はローカルキャッシュを使い続け、
アプリの挙動は変わりません。オリジンが落ちても、CDN が `stale-if-error` で最後に取得できた
オブジェクトを配り続けます。データベースが落ちても、コンフィグはオブジェクトストレージ上で自己完結
しているため、稼働中の実験は影響を受けません。

### この判断が受け入れる代価

1. **コンフィグは公開情報になります。** アプリのパッケージから誰でも取り出せるため、実験キーと
   パラメータは公開情報として扱います。未発表機能が実験キーから特定できてはならず、それを担保する
   命名規則は [`docs/08-operations-ja.md`](../../docs/08-operations-ja.md) に置きます。
2. **割当ロジックが複数言語に存在します。** そのため
   [`spec/bucketing-ja.md`](../../spec/bucketing-ja.md) を規範仕様とし、全実装を
   [`spec/golden-vectors.json`](../../spec/golden-vectors.json) で CI 検証します。リモート評価なら
   不要だった代価であり、これを意図して支払うことで可用性の利得が成立します。
3. **サーバ側のデータでターゲティングできません。** 属性はアプリが SDK に渡します。購買履歴の集計の
   ように、アプリが計算できない属性は、あらかじめセグメント ID として算出し、ログイン時にアプリへ
   配ります。
4. **バンドルは時間とともに大きくなります。** プラットフォーム別と SDK メジャーバージョン別に分割
   し、圧縮後 100KB を上限として監視します。

## 検討した代替案

- **リモート評価を主経路にする。** 却下します。アプリにとって唯一の緊急停止手段を動的サービスの
  背後に置くためです。秘匿性と実装の一本化という利点は実在します。とはいえ、デプロイで直せない経路
  における可用性の差のほうが重くなります。
- **リモート評価に、ローカルキャッシュのフォールバックを添える。** 両方の短所を取るため却下します。
  全インストールの初回起動では依然として動的サービスが必要で、フォールバック経路のために割当ロジック
  は結局端末に載り、しかも障害時にしか通らない第 2 の経路が増えます。テストされていない経路が、
  最もテストされていてほしい場面で走ることになります。
- **持続的接続でコンフィグを push し、変更を即時反映する。** 却下します。モバイルでソケットを開き
  続ける費用は電池と接続管理に跳ね返るうえ、得られる即時性は
  [BK-0005](../BK-0005-session-sealed-config/BK-0005-session-sealed-config-ja.md) が示すとおり
  望ましくありません。セッション途中で変更を適用すると、曝露の一意性が壊れます。
