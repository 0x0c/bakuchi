## はじめに

割当は、ユニット識別子を 0 から 9999 のバケットに写像し、バリアントがバケットの範囲を占有します。
この写像は Swift、Kotlin、Go、Python、TypeScript のすべてで再現できなければなりません。
[BK-0002](../BK-0002-local-evaluation/BK-0002-local-evaluation-ja.md) によって、割当ロジックが
それらすべてに存在するためです。本項目は、その写像に使うハッシュ関数を定めます。

この選択は事実上、後戻りできません。ハッシュを変えると全ユーザが再シャッフルされ、その時点で稼働
している実験がすべて無効になります。稼働中の実験がゼロの状態でしか実施できません。

## 動機

速度は目につきやすい基準ですが、適切な基準ではありません。MurmurHash3 は SHA-256 のおよそ 50 倍
速く、そしてこの用途の規模ではどちらも無関係です。起動時に 50 個のフラグを評価しても SHA-256 で
約 25 マイクロ秒であり、`start()` の予算 10ms の 0.25% にすぎません。ユーザに知覚できる差ではなく、
SDK のベンチマークにも表れません。

意味のある基準は**実装の一意性**です。同じ入力に対して、どの言語の標準的な実装も同じバイト列を
返すか、そして書き手が亜種を選ばずに済むか、という基準です。MurmurHash3 はこの基準を満たしません。
`x86_32`、`x86_128`、`x64_128` の亜種があり、同じ入力でも結果が食い違います。シードの読み方や末尾
バイトの扱いも実装ごとに異なります。Optimizely と GrowthBook がどちらも MurmurHash3 x86_32 を使って
いるため業界標準に見えますが、その選択はブラウザでの実行速度に動機があり、モバイルアプリには移し
かえられません。

MurmurHash3 の実装を 5 言語で一致させ、各言語のエコシステムが変化してもなお一致させ続けることは、
誰にも測れない速度差と引き換えに負う恒常的なリスクです。

## 詳細設計

### アルゴリズム

```
bucket(salt, unit_id):
    input  := UTF-8( salt + ":" + unit_id )
    digest := SHA-256(input)
    n      := uint32_big_endian(digest[0..4])
    return n mod 10000
```

規範的な記述と言語別の参照実装は [`spec/bucketing-ja.md`](../../spec/bucketing-ja.md) に置いています。

### 各要素の根拠

| 要素 | 選択 | 理由 |
|---|---|---|
| ハッシュ関数 | SHA-256 | すべての言語の標準ライブラリにあり、選ぶべき亜種が存在しません |
| 区切り文字 | `:` | 境界を固定し、`("ab", "c")` と `("a", "bc")` が衝突しないようにします |
| バイト取り出し | 先頭 4 バイト、ビッグエンディアン | どちらの語もどの言語でも曖昧さがありません。リトルエンディアンは環境依存の実装ミスを誘発します |
| バケット数 | 10000 | 1 basis point 単位で配分できます |

プラットフォーム標準のフレームワークから使えることも重要です。
[BK-0003](../BK-0003-native-sdks/BK-0003-native-sdks-ja.md) が SDK の第三者依存を禁じているため
です。iOS の `CryptoKit` と Android の `MessageDigest` はどちらも SHA-256 を追加費用なしで提供
します。MurmurHash3 を使うなら自前実装（上記のリスクそのもの）か外部依存（制約が禁じるもの）の
どちらかになります。

### 暗号学的強度は理由ではない

割当の予測は、防御対象の脅威ではありません。
[BK-0002](../BK-0002-local-evaluation/BK-0002-local-evaluation-ja.md) によりコンフィグは公開情報で
あり、誰でも自分のバケットを計算できるためです。SHA-256 を選ぶ理由は実装の一意性にあります。この
区別をここに記録しておくのは、将来の読み手が「十分に安全でありさえすれば、より速いハッシュに変えて
よい」と結論しないようにするためです。

### この選択が生む失敗の形

Java と Kotlin には符号なし 32 ビット整数がないため、`ByteBuffer.getInt()` でダイジェストを読むと
入力のおよそ半数で負値になり、しかも Java の `%` は被除数の符号を引き継ぎます。その結果、50/50 の
実験がおおよそ 75/25 に分かれます。例外は上がりません。規範仕様は符号なし読みを要求し、ゴールデン
ベクタが `uint32_be` を持つのは、まさにこの誤りを CI が発生地点で捕まえるためです。

## 検討した代替案

- **MurmurHash3 x86_32**（Optimizely と GrowthBook の選択）。動機の節で述べた亜種の曖昧性を理由に
  却下します。速度の優位は実在しますが、ここでは無関係です。
- **MD5。** 実装は一意で SHA-256 より高速ですが、FIPS 検証環境で禁止されることがあり、その場合
  ホストアプリによっては SDK を使えなくなります。SHA-256 にはその制限がありません。
- **棄却サンプリングによる剰余バイアスの補正。** バイアスは `7296 / 2^32`、およそ 100 万分の 1.7
  です。1 億ユーザを割り当てても期待値で 0.17 人分しか偏らず、いかなる検定統計量も変えません。
  補正すると各言語が同一に再現しなければならない分岐が増えるため、取り除くバイアスより大きな乖離
  リスクを生みます。
- **バケット数を 100 万などに増やす。** 却下します。1 basis point より細かい配分に運用上の用途が
  なく、範囲を広げても剰余バイアスは問題になる水準まで変わりません。
