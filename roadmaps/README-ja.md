# bakuchi ロードマップ

設計上の判断と、予定している変更は、すべて採番された **BK 項目**としてここに置き、日英の両方で
記述します。項目には、何を決めたか、なぜ決めたか、何を退けたかを記録します。判断を、記憶からの
蒸し返しではなく証拠に基づいて再検討できるようにするためです。

> このページが扱うのは、項目とは何か、どう追加するかです。個々の項目の現状は、ここの一覧ではなく
> `Status` への問い合わせで確認してください。
>
> ```bash
> python3 tools/roadmap_query.py --status "Proposal"
> ```

## Status の語彙

| 英語 | 日本語 | 意味 |
|---|---|---|
| `**Accepted**` | `**可決**` | 判断済み。実装は未着手です |
| `**Accepted, in progress**` | `**可決・実装中**` | 実装中です |
| `**Implemented**` | `**実装済み**` | 出荷済みです |
| `**Proposal**` | `**提案**` | 未決着です |
| `**Proposal (deferred)**` | `**提案（保留）**` | 意図して保留し、再開条件を記録してあります |

`Accepted` は、この形式の借用元の語彙に対して意図して追加した値です。bakuchi は設計段階の
リポジトリであり、コードが存在するよりずっと前に判断が決着します。その状態を `Proposal` と呼ぶと
実態より弱く、`Accepted, in progress` と呼ぶと実態より強くなります。

`Proposal (deferred)` には義務が伴います。再開条件を記録しないまま保留した項目は、誰も再検討しない
項目になります。書き方は
[BK-0007](BK-0007-revisit-kmp-shared-core/BK-0007-revisit-kmp-shared-core-ja.md) を参照してください。

## Topic

`プラットフォーム戦略`、`クライアント SDK 設計`、`コンフィグ配信`、`割当と決定性`、`データ基盤`、
`統計と解析`、`運用`

Topic は統制語彙であり、各値に日英の対応が固定されています。対応は
`tools/check_roadmap_format.py` が強制します。Topic を増やすには、このツールを編集します。

## 項目の追加

**BK 番号を自分で決めてはいけません。** `BK-XXXX` というプレースホルダで起票し、最後に番号を
割り当てます。並行して起票された項目どうしが衝突しないようにするためです。

```bash
# 1. 日英の雛形を生成する
python3 tools/new_roadmap_item.py --slug <slug> --title "<title>" --title-ja "<タイトル>" --topic "<topic>"

# 2. すべての TBD を、日英とも同じ密度で埋める

# 3. 番号を割り当てる（ディレクトリ名の変更と自己参照の書き換えを行います）
python3 tools/new_roadmap_item.py --allocate

# 4. 検証する
./tools/check.sh
```

**唯一の不変条件：`BK-XXXX` を項目のディレクトリの外に書いてはいけません。** 割当ツールが書き換える
のはそのディレクトリだけであるため、ほかの文書、仕様、コメントに書かれたプレースホルダは、古い参照
として残り続けます。

エージェントにこの手順を進めさせる場合は
[`ideation`](../.agent-workflows/ideation/workflow.md) ワークフローを使います。実行するコマンドは
どちらでも同じです。

## ファイル形式

各項目は、2 つのファイルを持つディレクトリです。

```
roadmaps/BK-NNNN-<slug>/
  BK-NNNN-<slug>.md      英語
  BK-NNNN-<slug>-ja.md   日本語
```

どちらのファイルも、次の 4 つを持ちます。

1. 言語切替リンク
2. `# BK-NNNN — <タイトル>` という見出し（em ダッシュ、U+2014）
3. `<!-- BK-METADATA -->` と `<!-- /BK-METADATA -->` で囲んだメタデータブロック
4. 順序の固定された 6 つの H2 セクション

| 英語 | 日本語 |
|---|---|
| `## Introduction` | `## はじめに` |
| `## Motivation` | `## 動機` |
| `## Detailed design` | `## 詳細設計` |
| `## Alternatives considered` | `## 検討した代替案` |
| `## Progress` | `## 進捗` |
| `## References` | `## 参考` |

6 つはすべて必須です。まだ書くことのないセクションは、省略せず `TBD` と書きます。項目に必要なその他
の内容は、6 つのいずれかの内側に H3 として置きます。

**メタデータを囲むフェンスは構造上の要です。** フェンスがあることで、パーサはその範囲の行だけを読み、
本文中に現れる同じ形の表を掴まずに済みます。メタデータのフィールドは次の順序で並べます。

| 順序 | 英語 | 日本語 | 必須 |
|---|---|---|---|
| 1 | `Proposal` | `提案` | 常に |
| 2 | `Author` | `提案者` | 常に |
| 3 | `Status` | `状態` | 常に |
| 4 | `Tracking issue` | `トラッキング Issue` | 任意 |
| 5 | `Implementing PR` | `実装 PR` | 出荷後 |
| 6 | `Topic` | `トピック` | 常に |
| 7 | `Related` | `関連` | 任意 |
| 8 | `Superseded by` | `後継` | 任意 |

## 日英を同じ密度で書く

日本語のファイルは英語版の要約ではなく、どちらももう一方の翻訳成果物ではありません。どちらの言語の
読み手も、論証の全体を受け取ります。起草にあたっては
[`document-writing`](../.agent-workflows/document-writing/workflow.md) と、書く言語のレイヤーを
併せて読んでください。これらの規範は下書きを形づくるものであり、あとから校正するためのものでは
ありません。

## 何が検査され、何が検査されないか

`tools/check_roadmap_format.py` は形式を判定します。言語切替リンク、H1 の形、メタデータのフェンスと
フィールド順序、Status の語彙、Status と Topic の日英対応、6 つのセクション見出しです。textlint は
文章の表記を判定します。**どちらも論証は判定しません。** 項目が主張から書き出せているか、代替案が
公平に扱われているか、保留に再開条件が記録されているか。これらはレビュー時に人が確認する期待値です。

## 未整理のアイデア

> まとまっていない着想はここに書き、範囲が定まった時点で採番された項目に昇格させます。

- **`docs/` と `spec/` を文章規範の対象に入れる。** どちらも規範を導入する前に書いたもので、
  まだ適合していません（`docs/` に 30 件、`spec/` に 7 件の指摘）。そのため `tools/check.sh` は
  ロードマップ項目とルート直下の README だけを対象にしています。移行は機械的ですが量が多いため、
  採番する前に範囲を決めます。
- **`docs/` の二言語化。** 設計ドキュメントは日本語だけです。ロードマップ項目と同じように対を
  用意すれば、リポジトリ全体をどちらの言語でも読めるようになります。
