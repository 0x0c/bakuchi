## はじめに

iOS と Android には、同一の挙動をする SDK が必要です。割当について 2 つの実装がずれると、実験結果は
静かに誤ります。例外は上がらず、テストも落ちず、数値はもっともらしく見えたままです。問題は、両者が
一致することをどう保証するかにあります。

本項目では、Swift と Kotlin の独立した 2 実装を出荷し、両者の一致を共有コードではなく、規範仕様と
共通のゴールデンベクタで保証します。

## 動機

直感的な答えは、ロジックを共有することです。Kotlin Multiplatform のコアを置くか、Rust のコアを
生成バインディングの背後に置けば、1 つの実装が両方のプラットフォームに使えます。2 実装が乖離すると
いうよくある問題に対する、よくある処方です。しかしここでは、3 つの事実がこの処方に反対します。

**ずれてはならない部分は小さい。** 厳密に一致する必要があるのは決定的割当だけで、それは数十行しか
ありません。SHA-256 のダイジェスト、4 バイトのビッグエンディアン読み、累積レンジ探索です。共有コード
が保証するのは「同じコードが両方で動くこと」です。ゴールデンベクタが保証するのは「同じ**答え**が出る
こと」です。本当に欲しいのは後者であり、テストは後者を代理ではなく直接に主張します。本プラット
フォームの設計時には、Python、Node、Go の独立した 3 実装が同一のベクタを再現することを確認しました。
規範仕様とベクタがあれば、言語をまたいだ一致を保てることの根拠になります。

**バイナリサイズは交渉可能な要件ではない。** 実験基盤の SDK を入れるとアプリが 3MB 増えると伝えれば、
iOS チームはその SDK を拒否します。Kotlin/Native のランタイムは、ユーザにとってのアプリの価値では
ない部品に対して正当化しにくい費用です。そして、導入されない SDK には価値がありません。

**残りの部分はそもそも共通化できない。** キャッシュ、イベント送信、バックグラウンド処理は、
プラットフォームごとにまったく異なる機構を使います。バックグラウンド送信は iOS では `URLSession`、
Android では `WorkManager` を通ります。永続化は一方がファイルシステムと Keychain、他方が DataStore
と暗号化設定です。ライフサイクルの通知も別々のフレームワークから来ます。本当に共通化できるのは薄い
オーケストレーション層だけで、クロスプラットフォームのツールチェーンの費用に見合いません。

## 詳細設計

### 秤にかけた選択肢

| 選択肢 | iOS のバイナリ増分 | ロジック共有 | 導入障壁 |
|---|---|---|---|
| **ネイティブ 2 実装（Swift と Kotlin）** | 約 200KB | なし。規範仕様とテストで担保します | 低い |
| Kotlin Multiplatform | 1.5MB から 3MB 増 | あり | 高い。iOS チームの同意が要ります |
| Rust コアと生成バインディング | 約 400KB | あり | 中から高。ビルドが複雑で、書ける人が限られます |

### プラットフォームごとの選択

| 項目 | iOS | Android |
|---|---|---|
| 言語 | Swift 5.9 以降、strict concurrency | Kotlin 2.0 以降 |
| 最低サポート | iOS 15 | API 24 |
| 配布 | Swift Package Manager。CocoaPods も併走します | Maven Central（AAR） |
| 永続化 | ファイルシステム。`install_id` のみ Keychain | DataStore と暗号化設定 |
| ネットワーク | `URLSession`。依存なし | `OkHttp`。多くのアプリが既に持っています |
| バックグラウンド送信 | `URLSession` の background configuration | `WorkManager` |

**SDK は第三者ライブラリに依存しません。** ホストアプリとのバージョン衝突は導入の最大の障壁である
ため、好みではなく強い制約として扱います。この制約は
[BK-0004](../BK-0004-bucketing-hash/BK-0004-bucketing-hash-ja.md) のハッシュ選択にも効きます。
SHA-256 はプラットフォーム標準の暗号フレームワークから追加費用なしで使えます。

### この判断を安全にする統制

以下の統制がそろわないかぎり、ネイティブ 2 実装は単に間違える機会が 2 つあるだけになります。

1. [`spec/bucketing-ja.md`](../../spec/bucketing-ja.md) を**規範**とします。各実装が従う先は、互いの
   コードではなく規範仕様です。
2. 全実装が [`spec/golden-vectors.json`](../../spec/golden-vectors.json) を CI で検証し、
   **不一致であればマージをブロック**します。
3. ベクタは最終的なバケットに加えて中間値（`sha256_prefix_hex` と `uint32_be`）も持ちます。
   不一致が起きたとき、ずれた事実だけでなく、**どこで**ずれたかを特定できます。
4. ターゲティングオペレータを追加するときは、**両実装を同一の PR で更新**します。片方のプラット
   フォームにしかオペレータがない状態は作りません。
5. 両実装に前方互換テストを置きます。未知のフラグ型、未知のバリアント、未知のオペレータは、
   クラッシュではなく呼び出し側のデフォルトに解決される必要があります。

## 検討した代替案

- **Kotlin Multiplatform の共有コア。** 却下しますが、技術そのものの評価ではなく、バイナリサイズと、
  生成される Swift 側の使い勝手を理由とします。再評価の条件は再議論に委ねず、
  [BK-0007](../BK-0007-revisit-kmp-shared-core/BK-0007-revisit-kmp-shared-core-ja.md) に記録
  しました。
- **Rust コアと生成バインディング。** バイナリは最小で性能も最良ですが、ビルドパイプライン
  （`xcframework` と Android NDK の成果物）と、保守できるエンジニアの層の薄さが、この規模では利得を
  上回ります。
- **割当関数だけを小さなライブラリとして共有する。** 却下します。数十行のためにクロスプラット
  フォームのビルドを持ち込む価値はなく、ゴールデンベクタが既に同じ範囲を覆っています。
